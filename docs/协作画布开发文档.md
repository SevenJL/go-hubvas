# 多人实时协作画布 —— 开发文档

> 版本:v1.0
> 技术栈:Go(后端) + React(前端)
> 文档目标:为团队提供从架构、模块设计、协议、数据模型到部署与开发计划的完整实现指南。

---

## 1. 项目概述

### 1.1 一句话定位
一个支持百人级实时协作的在线画布产品:多人可同时在同一画布上绘制,并能将作品发布到社区进行分享、点赞、Fork 与二次创作。

### 1.2 核心目标
- 单画布支持 **≥ 100 人同时实时编辑**,延迟可感知地低(本地操作即时响应,远端同步 < 200ms 为目标)。
- 协作过程保证 **最终一致性**:任何用户在任意网络状况下(含断线重连、离线编辑)最终看到相同画布。
- 提供完整的 **社区生态**:发布、浏览、Fork、点赞、评论、关注。
- 后端具备 **水平扩展能力**,单房间不绑定单台服务器。

### 1.3 非目标(本期不做)
- 像素级实时音视频会议(仅做文字聊天,语音为后续迭代)。
- 移动端原生 App(先做 Web,移动端用响应式页面过渡)。

## 3. 系统架构

### 3.1 总体分层

```
┌──────────────────────────────────────────────────────────┐
│                         客户端 (React)                       │
│   绘图引擎(tldraw/Konva) + CRDT(Yjs) + WebSocket Client   │
└───────────────┬──────────────────────────┬─────────────────┘
                │ WebSocket(实时)          │ HTTPS(REST)
        ┌───────▼───────┐          ┌────────▼─────────┐
        │  实时协作服务    │          │   业务 API 服务    │
        │ (WS Gateway +  │          │ (用户/画布/社区)   │
        │  Room/Hub)     │          └────────┬─────────┘
        └───┬───────┬────┘                   │
            │       │                         │
   ┌────────▼─┐  ┌──▼──────────┐    ┌─────────▼────────┐
   │  Redis   │  │ NATS/Redis  │    │   PostgreSQL     │
   │(presence)│  │  Pub/Sub    │    │  (元数据/社交)    │
   └──────────┘  │ (跨节点扇出) │    └──────────────────┘
                 └─────────────┘
                        ┌──────────────────┐
                        │  MinIO / S3       │
                        │ (快照/导出/素材)   │
                        └──────────────────┘
```

### 3.2 房间(Room/Hub)模型 —— 并发核心

每个画布对应一个 **Room**,由一个独立 goroutine 串行管理状态,所有操作经 channel 进入,处理后广播。这样**无需对画布状态加锁**。

```
每个连接:
  - readPump  goroutine:阻塞读取客户端消息 → 投递到 Room 的 inbound channel
  - writePump goroutine:从该连接的带缓冲 send channel 取消息 → 写入 WebSocket

每个房间:
  - hub goroutine:从 inbound channel 取 op → 校验/合并 → 写入持久化队列 → 广播到所有成员 send channel
```

> **100 人 ≈ 200+ goroutine/房间**,对 Go 调度器毫无压力。

### 3.3 冲突解决方案(关键决策)

采用 **CRDT 中继方案(推荐)**:

- 前端使用 **Yjs** 维护画布的 CRDT 文档,本地操作即时生效。
- Go 服务端作为 **中继 + 持久化层**:接收 Yjs 二进制 `update`,转发给同房间其他成员,并周期性持久化文档快照。
- 优势:**合并冲突、离线编辑、断线重连一致性全部由 CRDT 自动保证**,服务端不需要实现复杂的 OT/合并算法,只做权限校验与扇出。

> 备选方案(自研服务端权威状态):每个图形对象用 `last-write-wins + 版本号`,图层顺序用**分数索引(fractional indexing)**。仅当需要强服务端管控(如严格审计、服务端校验每一笔操作)时采用,实现成本更高。

## 4. 技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 后端语言 | **Go 1.22+** | 高并发、goroutine 模型天然契合长连接 |
| WebSocket | **coder/websocket** | gorilla 已归档;coder/websocket 基于 context、并发写安全、活跃维护 |
| 超高连接数场景(可选) | gws / quickws / nbio | 仅当单机需冲十万级以上连接时考虑 |
| HTTP 框架 | **Gin**(或 Fiber/Echo) | REST API:登录、画布、社区 |
| 跨节点扇出 | **NATS**(或 Redis Pub/Sub) | 同房间用户落在不同节点时互通,NATS 吞吐更优 |
| 关系数据库 | **PostgreSQL 15+** | 用户、画布元数据、社交关系 |
| 缓存 / 在线状态 | **Redis** | presence、光标、房间成员、限流计数 |
| 对象存储 | **MinIO / S3** | 快照、导出文件、上传素材 |
| 认证 | **JWT** | 短期 access + 刷新 token |
| 前端框架 | **React + TypeScript** | |
| 绘图引擎 | **tldraw / Konva / Fabric.js** | 不要从零造绘图层 |
| CRDT | **Yjs** | 前端 CRDT,服务端中继 |
| 部署 | **Docker + Kubernetes** | Nginx 入口需开启 WebSocket Upgrade |
| 可观测 | Prometheus + Grafana + OpenTelemetry | 连接数、房间数、消息速率、延迟 |

> 选型提醒:`gorilla/websocket` 仍可用但已归档;`coder/websocket` 的并发写内部安全,可规避「多 goroutine 同时写导致帧损坏/panic」这一最常见的生产 bug。

## 5. 核心模块设计

### 5.1 连接管理(WS Gateway)

职责:
1. 升级 HTTP 为 WebSocket,校验 JWT 与画布访问权限。
2. 解析 URL 中的 `canvasID`,把连接注册到对应 Room(不存在则创建)。
3. 为连接启动 readPump / writePump。

关键防护:
- **写超时 + 带缓冲 send channel**:某个慢客户端不能拖垮整个房间。channel 满则丢弃该连接(踢下线,客户端自动重连补齐)。
- **心跳**:Ping/Pong + 读超时,清理僵尸连接。
- **单连接限流**:令牌桶,防止恶意客户端刷消息。

### 5.2 Room 生命周期

- **创建**:首个用户加入时懒加载;从对象存储拉取最近快照载入内存。
- **运行**:串行处理 op → 持久化队列 → 广播;光标类高频消息单独节流(30~60fps)与批处理。
- **持久化**:增量写入 + 定时/定量快照(如每 N 次 op 或每 30s)。
- **卸载**:房间空闲超时(如 5 分钟无人)→ 落盘 → 从内存释放,实现内存冷热分离。

### 5.3 跨节点扇出

当部署多实例时:
- 每个 Room 订阅 NATS subject `canvas.{canvasID}`。
- 本地处理完 op 后,既广播给本机成员,也 publish 到 NATS。
- 其他节点上同房间的 Room 收到后广播给各自本地成员。
- 入口层用**一致性哈希**尽量把同房间用户路由到同一节点,减少跨节点流量(优化项,非必须)。

### 5.4 Presence(在线状态)

- 用 Redis 存房间成员、光标位置(短 TTL,靠心跳续期)。
- 成员加入/离开/光标移动作为独立的轻量消息类型广播,不进 CRDT 文档。

## 6. 数据模型(PostgreSQL)

```sql
-- 用户
CREATE TABLE users (
  id           BIGSERIAL PRIMARY KEY,
  username     VARCHAR(50) UNIQUE NOT NULL,
  email        VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  avatar_url   TEXT,
  created_at   TIMESTAMPTZ DEFAULT now()
);

-- 画布
CREATE TABLE canvases (
  id           BIGSERIAL PRIMARY KEY,
  owner_id     BIGINT REFERENCES users(id),
  title        VARCHAR(200) NOT NULL,
  snapshot_key TEXT,                 -- 对象存储中最新快照的 key
  visibility   SMALLINT DEFAULT 0,   -- 0私有 1公开(已发布)
  forked_from  BIGINT REFERENCES canvases(id), -- Fork 来源
  created_at   TIMESTAMPTZ DEFAULT now(),
  updated_at   TIMESTAMPTZ DEFAULT now()
);

-- 协作成员与权限
CREATE TABLE canvas_members (
  canvas_id    BIGINT REFERENCES canvases(id),
  user_id      BIGINT REFERENCES users(id),
  role         SMALLINT NOT NULL,    -- 0所有者 1可编辑 2只读 3仅评论
  PRIMARY KEY (canvas_id, user_id)
);

-- 邀请
CREATE TABLE invitations (
  id           BIGSERIAL PRIMARY KEY,
  canvas_id    BIGINT REFERENCES canvases(id),
  token        VARCHAR(64) UNIQUE NOT NULL,
  role         SMALLINT NOT NULL,
  expires_at   TIMESTAMPTZ
);

-- 社区:点赞 / 收藏 / 评论 / 关注 / 标签(略举两例)
CREATE TABLE likes (
  user_id   BIGINT REFERENCES users(id),
  canvas_id BIGINT REFERENCES canvases(id),
  created_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (user_id, canvas_id)
);

CREATE TABLE comments (
  id         BIGSERIAL PRIMARY KEY,
  canvas_id  BIGINT REFERENCES canvases(id),
  user_id    BIGINT REFERENCES users(id),
  content    TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

> 画布的**图形数据本身不入库**,以 CRDT 二进制快照形式存对象存储,DB 仅存元数据与社交关系。

## 8. WebSocket 协议设计

连接地址:`wss://host/ws?canvas=<canvasID>&token=<jwt>`

消息统一为 JSON 信封(CRDT 二进制 payload 用 base64 或独立二进制帧):

```jsonc
{
  "type": "sync" | "awareness" | "presence" | "chat" | "ack" | "error",
  "seq": 12345,            // 客户端自增序号,用于 ack
  "payload": { /* 按 type 定义 */ }
}
```

| type | 方向 | 含义 |
|------|------|------|
| `sync` | 双向 | Yjs 文档更新(增量 op);新成员加入时服务端先推全量快照 |
| `awareness` | 双向 | Yjs awareness:光标、选区、编辑中对象 |
| `presence` | 下行 | 成员加入/离开、在线列表 |
| `chat` | 双向 | 房间聊天消息 |
| `ack` | 下行 | 对某个 `seq` 的确认 |
| `error` | 下行 | 权限/限流/异常 |

入房流程:
1. 客户端连接 → 服务端校验 token 与权限。
2. 服务端推送 `presence`(在线列表)+ `sync`(全量快照)。
3. 之后双方仅交换增量 `sync` / `awareness`。

性能约定:
- `awareness`(光标)客户端节流到 ≤ 60fps;服务端对其再做合并广播。
- `sync` 增量可按 16~50ms 窗口批处理后再扇出。

## 9. 并发与扩展性要点

1. **单房间单 goroutine 串行**:消除锁竞争,状态变更可预测。
2. **每连接独立带缓冲 send channel + 写超时**:隔离慢客户端,避免一人卡全房间。
3. **冷热房间分离**:空闲房间落盘卸载,控制内存。
4. **跨节点 Pub/Sub**:房间不绑定单机,支持水平扩容。
5. **入口一致性哈希**(可选):减少跨节点流量。
6. **限流**:连接级 + 用户级令牌桶,保护 hub goroutine。
7. **快照压缩**:CRDT 文档定期 GC/压缩历史,避免快照无限膨胀。

## 10. 部署架构

- **Nginx / Ingress**:TLS 终止 + WebSocket Upgrade,长连接需调大 `proxy_read_timeout`。
- **实时服务**与**业务 API 服务**独立部署、独立扩缩容(长连接服务对扩缩容更敏感,需优雅排空)。
- **Redis / NATS / PostgreSQL / MinIO** 用托管或独立 StatefulSet。
- **优雅停机**:实例下线前停止接收新连接,通知客户端重连到其他节点,落盘后退出。
- **监控指标**:活跃连接数、活跃房间数、每房间消息速率、广播延迟 P99、goroutine 数、内存。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 光标/高频消息打爆带宽 | 卡顿、成本高 | 节流 + 批处理 + 合并广播 |
| 慢客户端拖垮房间 | 全员卡顿 | 带缓冲 channel + 写超时 + 踢线 |
| 单房间内存膨胀 | OOM | 冷热分离 + 快照压缩/GC |
| 跨节点同步延迟 | 不一致体感 | 一致性哈希降低跨节点 + CRDT 保最终一致 |
| 长连接服务扩缩容抖动 | 大量重连 | 优雅排空 + 客户端指数退避重连 |
| CRDT 快照无限增长 | 加载变慢 | 定期合并/压缩历史 |

## 13. 验收标准(关键)

- [ ] 单画布 100 人同时绘制,本地操作即时响应,远端同步 P99 < 200ms(局域/同区域)。
- [ ] 任一用户断网 5 分钟后重连,画布状态自动补齐一致。
- [ ] 压测:单房间 100 连接持续绘制 10 分钟,无消息丢失导致的最终不一致。
- [ ] 多实例部署下,不同节点的同房间用户实时互通。
- [ ] 社区发布的画布可被他人 Fork 并独立编辑,互不影响。
